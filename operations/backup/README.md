# Encrypted daily backup — operational activation required

Scheduled backups are disabled unless `BACKUP_ENABLED=true`. A manual dispatch with `initial_verification=true` permits the approved first backup/restore/delivery check while the schedule remains disabled. Code/tests are not evidence of a successful Production backup. Do not enable the schedule until secrets, PostgreSQL client availability, first delivery and isolated restore have been verified. No application code, schema, migration or Hostinger configuration is changed by these files.

## Approved destinations and access

Only notification recipient: `marwanalsawi@alzaad.org.sa`, through the already configured SMTP provider. Daily archives are stored encrypted in the existing private object storage bucket, under the fixed separate prefix `alzad-encrypted-backups/`, with a unique backup identifier and conditional creation (`IfNoneMatch: '*'`) for every object to prevent overwriting. Archives larger than 8 MiB are stored as independent numbered objects `<id>.enc.part-0001`, `<id>.enc.part-0002`, and so on; each object is at most 8 MiB. Archives of 8 MiB or less retain the single `<id>.enc` filename. This respects the existing per-file limit without changing storage settings or completing an S3 multipart upload into an oversized single object. No ACL changes, public access, public download URL, email attachment or additional recipient. No new bucket, service, dependency, configuration field or workflow secret is required. The existing GitHub environment `production-backup` remains restricted to `platform/node-migration`, using environment secrets `ALZAD_BACKUP_CONFIG` (JSON) and `BACKUP_PUBLIC_KEY` (RSA public PEM). Never add a private recovery key to GitHub or upload it to object storage. Keep secrets unavailable to pull-request/test/install steps; do not enable debug logging.

Configuration JSON fields (names only): `DATABASE_URL` (direct or session pooler, not transaction pooler), `EXPECTED_DB_HOST`, `EXPECTED_DB_NAME`, `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_REGION`, `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`, `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_FORCE_PATH_STYLE`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME`. Reuse the existing approved values and credentials; never commit or print them. Database access remains read-only. The existing object credentials must already permit reading application objects and creating/reading the encrypted backup object; an access failure must fail the backup without changing credentials, configuration or permissions.

## Scope and safety

Custom pg_dump of public schema, including application data and Prisma migration history; read-only session, TLS, bounded command, no seed/migration/SQL delete. Every dump must actually restore successfully in its own disposable PostgreSQL 18 container with **no network**, no Production credentials, and a read-only dump mount before email is sent. Technical policy roles are created only inside that container. Restored table counts and migration presence are recorded inside the encrypted manifest; this is not a full application/portal acceptance test. Only that uniquely named container and its volumes are removed afterwards. The official PostgreSQL image and Actions are pinned to verified digests/commits.

Private bucket objects, keys and content metadata are collected separately, ETag/size/checksum verified. Only keys starting with the exact fixed `alzad-encrypted-backups/` prefix are excluded from both before/after listings so stored archives, numbered parts and partial failed runs cannot recursively enter later backups. All other objects remain included and changes mid-copy still fail the backup. Every `files` row in the isolated restored database must have an archived object with the expected bucket/checksum; references are never skipped, including application references that misuse the backup prefix. DB and object storage still have **no shared atomic snapshot**; this check prevents a known missing referenced file from being reported as a successful backup, but cannot prove global point-in-time consistency. No PostgreSQL role passwords, Supabase internal schemas, service secrets or deployment settings included: preserve those separately in an approved secure vault. The manifest and clear data are inside an RSA-OAEP + AES-256-GCM encrypted archive. Only encrypted bytes are uploaded, through bounded file-range streams. Every part is read back and must match its exact local byte count and SHA256. The readback bytes, accumulated in numbered order, must also match the complete local encrypted archive's size and SHA256 before the single success notification is sent. The notification includes the identifier, part count, ordered filename range, total bytes and full-file SHA256, with no attachment or download URL. An upload/readback/checksum failure, including failure partway through a run, sends no success email and leaves previously stored parts untouched. Such partial sets are not successful backups. Notification failure fails the run but leaves the verified stored archive intact; no automatic object deletion is performed. SMTP acceptance is not Inbox delivery proof.

The historical `sendParts` helper and its tests remain available for older email-based backups: exact 8 MiB numbered attachments, a 48 MiB warning and a 64 MiB hard limit. Daily storage delivery no longer uses this helper or the email attachment limit. Existing bucket capacity and notification receipt require owner monitoring; no paid service, storage expansion or automatic retention deletion is enabled.

## Owner key custody

Create an owner-only external directory, run `node operations/backup/recovery.mjs generate-keys DIRECTORY`. Preserve `recovery-private.pem` offline in at least two owner-controlled protected locations. Do not email it alongside backups, commit it, put it in GitHub Secrets or upload it to object storage. Losing it makes backups unreadable. Only `encryption-public.pem` is uploaded to GitHub. Retain historical email parts for five months and monitor mailbox capacity. Stored encrypted archives remain in the existing private bucket without automatic deletion; no new retention automation or paid storage expansion.

## Verification and restore — never over Production

1. Run `node --test operations/backup/backup.test.mjs` (synthetic fixtures, no DB/SMTP connection).
2. Confirm client version is not older than server and environment branch restrictions/secrets, then manual dispatch only from Production branch with `initial_verification=true`; leave `BACKUP_ENABLED` unset until this check succeeds.
3. Verify every expected stored part and the complete encrypted archive's byte count and full-file SHA256, and actual owner receipt of the notification with the matching identifier and part count. Action result `SMTP_ACCEPTED` alone is insufficient; a partial set from a failed run must not be treated as a successful backup.
4. Download all matching encrypted parts locally through authenticated private storage access. Use only one backup identifier and supply all parts in exact numeric order (`.part-0001`, `.part-0002`, through the notification's final part). Check that their total bytes and the SHA256 of their concatenated bytes match the notification. Do not generate a public or emailed download link. The existing command `node operations/backup/recovery.mjs decrypt PRIVATE_KEY OUTPUT.tar.gz PART1 PART2 ...` concatenates parts in the supplied order and authenticates all bytes before writing; missing, reordered or modified parts fail authentication. It never overwrites output or restores automatically. For a single-object backup, supply `BACKUP.enc` as the only part; historical email parts use the same ordered command. For archives too large for workstation memory use a reviewed streaming recovery tool instead.
5. Extract archive into a new protected directory. Validate database dump and all object hashes from manifest. Use an isolated empty PostgreSQL database on loopback with a test-only name, **not any production URL/credential**. `pg_restore --exit-on-error --no-owner --no-acl --dbname TEST_DATABASE database.dump`; no `--clean`, no Production target.
6. Restore objects into a separate private isolated test bucket preserving keys/content type. Verify migration/table counts, file references, private file access, login and tenant isolation without triggering email or operational schedulers. Never run destructive E2E cleanup on restored real data.
7. Record UTC date, source backup identifier/checksum, isolated environment, duration, record/object counts, validation results, limitations and responsible owner. Activation is not complete until this evidence exists.
