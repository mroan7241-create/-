# نظام متابعة توزيع الأجهزة — جمعية الزاد

تطبيق ويب على Google Apps Script، بالشراكة مع مؤسسة سليمان أبانمي الأهلية.

## الملفات

الخادم مقسَّم إلى 16 ملف `.gs` موضوعيًا بدل ملف واحد ضخم. **Google Apps
Script يدمج كل ملفات `.gs` في مشروع واحد ضمن نطاق عام واحد تلقائيًا، بصرف
النظر عن اسم الملف أو ترتيبه** — لا "استيراد" ولا "تصدير" بينها، وكل دالة
أو ثابت مُعرَّف في أي ملف متاح للجميع فورًا. لذلك لا يوجد أي ترتيب إلزامي
لإضافتها في المحرر.

| الملف | الدور |
|---|---|
| `Config.gs` | الإعدادات العامة، أسماء الأوراق والأعمدة، الثوابت المشتركة |
| `ReferenceData.gs` | المصادر المرجعية (مناطق/مدن/تصنيفات)، ترحيلها الآمن |
| `Auth.gs` | تسجيل الدخول، الجلسات، تحديد المعدّل، الصلاحيات |
| `Bootstrap.gs` | بناء بيانات كل بوابة (إدارة/جمعية/مندوب)، والحزمة المُجمَّعة `getPortalBundle` (جولة واحدة بدل ثلاث)، وملخّص `dashboardModules` لبوابة الإدارة (بلا أي قراءة إضافية) |
| `Beneficiaries.gs` | حفظ المستفيدين، منع التكرار (مؤكَّد/محتمل)، الاستيراد الجماعي، الموقع الجغرافي |
| `ExcelTemplate.gs` | يبني قالب استيراد المستفيدين بصيغة `.xlsx` حقيقية (OOXML عبر `Utilities.zip`) — CSV يبقى بديلًا احتياطيًا |
| `Delegates.gs` | المناديب، التسليم، التعذّر و«إعادة المحاولة» الصريحة، سجل المحاولات، تأكيد التسليم وإثباته |
| `DevicesAssociations.gs` | الأجهزة، وإدارة حسابات الجمعيات |
| `Applications.gs` | بوابة تقديم الجمعيات العامة (3 مراحل: بيانات/أسئلة قبول/مرفق وإقرار) ودورة الاعتماد — `clientRequestId` دائم لإرسال idempotent، honeypot، رفع ملف ترخيص خاص محقَّق التوقيع، `getApplicationStatus` للاستعلام الآمن بعد مهلة الواجهة |

| `Pagination.gs` | ترقيم الصفحات والبحث والترتيب العامان — يستخدمها كل `list*()` |
| `Normalize.gs` | تحويل صفوف الأوراق إلى كائنات جاهزة للواجهة، ودوال `list*`/`getAuditRows_` المُرقَّمة |
| `DataUtils.gs` | القراءة/الكتابة في Sheets، ذاكرة الطلب الواحد، قياس الأداء (`traceId`)، توليد المعرّفات ورفض المكرَّر منها |
| `Validation.gs` | التحقق من المدخلات، التشفير، منع الحقن |
| `ReleaseOps.gs` | `preflightRelease_(token)` (قراءة فقط) و`applyReleaseSchema_(token, options)` (إضافي فقط) — كلاهما خاص ومقفل خلف رمز وصول صيانة مؤقت (`grantMaintenanceAccess_`)، بديل آمن لاستخدام `setupSheets_()` مباشرة كخطوة نشر عامة متكررة |
| `Index.html` | الواجهة الكاملة: HTML + CSS + JavaScript (ملف واحد). يحمّل Leaflet/OpenStreetMap كسولًا فقط عند فتح نموذج موقع المستفيد (مجانيان بالكامل، بلا مفتاح API) — مصدرا خطوط Google Fonts هما الموردان الخارجيان الآخران الوحيدان |
| `DEPLOYMENT.md` | دليل تركيب ونشر تنفيذي: المتطلبات، النسخ الاحتياطي، preflight/dry-run/تطبيق المخطط، نشر تجريبي، اختبار البوابات الأربع، معايير القبول، الرجوع |
| `SECURITY_REVIEW.md` | مراجعة أمنية برمجية ومحاكاة: جرد كامل لكل دالة Apps Script (الدور/الجلسة/الملكية/الكتابة)، مصفوفة الصلاحيات وIDOR، الأسرار، رفع الملفات، الروابط الخارجية |
| `tools/gs-manifest.js` | ترتيب دمج ملفات .gs لأدوات الاختبار المحلية فقط (لا علاقة له بـ Apps Script) |
| `tools/verify.js` | فاحص ثابت: سلامة JS، توازن البنية، أنماط النشر الخطرة، مطابقة الاستدعاءات |

| `tools/server-test.js` | اختبار منطق الخادم: التحقق، التنقية، الأمان، ثبات بنية الجداول، دورة اعتماد الجمعيات |

| `tools/perf-bench.js` | قياس تجريبي لعدد قراءات الشيت قبل/بعد تحسينات الأداء الأولى (لا يُنسخ للنشر) |
| `tools/drive-mock.js` | محاكاة DriveApp/Utilities.newBlob تخزّن المحتوى فعليًا (لا كائنات صورية فارغة) — لازمة لاختبار رفع/قراءة/حذف ملف الترخيص في بيئة Node |
| `tools/application-fixtures.js` | حمولة طلب انضمام جمعية صالحة وكاملة (الحقول الـ18 الجديدة كافة) تُستخدَم في كل ملفات الاختبار بدل تكرار بنائها |
| `tools/preview.js` | يبني `tools/.preview/preview.html` بحقن بيانات وهمية بدل `google.script.run`، لمراجعة الواجهة بصريًا (لقطات شاشة/متصفح محلي) دون نشر المشروع أو الاتصال بأي Sheet حي — الملف الناتج للمعاينة فقط ولا يُنسخ إلى Apps Script |

مجلدا `tools/` و`assets/` أدوات تطوير فقط — **لا يُنسخان إلى مشروع Apps
Script**. الملفات التي تُنسخ فعليًا إلى Apps Script هي ملفات `.gs`
الستة عشر أعلاه بالإضافة إلى `Index.html`.

## تشغيل الفحوص

```bash
node tools/verify.js
node tools/smoke.js
node tools/server-test.js
node tools/security-test.js
node tools/state-test.js
node tools/account-test.js
node tools/perf-test.js
node tools/reference-test.js
node tools/integration-test.js
```

يجب أن تنجح التسعة (فحص ثابت + تشغيلي + منطق خادم + مراجعة أمنية آلية +
سلامة الحالات + إدارة الحسابات + الأداء الوظيفي + البيانات المرجعية + رحلة
تكامل كاملة عبر البوابات الثلاث) قبل أي نشر.
`tools/perf-bench.js` و`tools/perf-scale-test.js` أدوات قياس/تقرير
اختيارية، ليست جزءًا من بوابة النجاح/الفشل (لا تفشلان، تطبعان تقريرًا فقط).

**ملاحظة صادقة عن `tools/security-test.js`**: فحص آلي على مستوى الكود
والمنطق داخل بيئة محاكاة (Node.js vm)، وليس اختبار اختراق مستقلًا بمعايير
OWASP/PTES يغطي الشبكة والبنية التحتية والنشر الفعلي. مفيد لرصد الانحدار
الأمني آليًا بعد كل تعديل، ولا يغني عن مراجعة أمنية مستقلة احترافية قبل
أي إطلاق واسع النطاق.

## أصول الهوية البصرية

**مُضمَّنان فعليًا بالفعل** — لا خطوة يدوية مطلوبة. الشعاران محفوظان
كملفين ثنائيين مرجعيين في `assets/` (`assetsalzad-logo.png.png`/
`assetsabanumay-logo.png.png`)، ومُضمَّنان مسبقًا كـ`data:image/png;base64,...`
داخل ثابت `BRAND` في أعلى كتلة JavaScript بـ`Index.html` — بالضبط الحل
الآمن المطلوب لـ HtmlService (لا مسار ملفات GitHub محلي هشّ يعتمد عليه
Apps Script، ولا رابط خارجي). إن احتجت **استبدال** أحد الشعارين لاحقًا
بنسخة محدَّثة:

```powershell
# ويندوز (PowerShell)
"data:image/png;base64," + [Convert]::ToBase64String([IO.File]::ReadAllBytes("zad-logo.png")) | Set-Clipboard
```

```bash
# macOS أو Linux
printf 'data:image/png;base64,%s' "$(base64 -w0 zad-logo.png)" | pbcopy
```

ثم استبدل قيمة `zadLogo`/`partnerLogo` في `Index.html` بالناتج كاملًا.
**شروط الأصل الجديد**: PNG بخلفية شفافة أو SVG (لا خلفية بيضاء/سوداء
مدمجة)، بلا قص أو تمديد أو ظل أو حد، ونسبة الشعار الأصلية كما هي. تحقّق
من قناة الشفافية عبر:

```bash
python3 -c "import struct,sys; d=open(sys.argv[1],'rb').read(); print('نوع اللون:', struct.unpack('>B', d[25:26])[0], '(6 أو 4 = يحمل شفافية)')" zad-logo.png
```

`tools/smoke.js` يتحقق آليًا أن كلا الشعارين مُضمَّنان فعليًا كبيانات
base64 صحيحة (لا نص فارغ) عند كل تشغيل.

### شكل الـ Lockup

الزاد دائمًا في الصف الأول بوصفه الشعار الرئيسي، والشريك في صف مستقل تحته
يفصله خط رفيع هادئ مع عبارة «بالشراكة مع». لا يُدمج الشعاران في شكل واحد،
ولا يتكرر شعار الشريك بوصفه عنصرًا زخرفيًا في أي مكان آخر من الواجهة.

## الأداء (المرحلة الثالثة)

- **مهلة موحّدة لكل استدعاء خادم** (`API_TIMEOUT_MS` في `Index.html`، 25
  ثانية): عند تجاوزها تظهر رسالة صريحة توصي بالتحقق قبل إعادة المحاولة
  (لا تُعرض كنجاح ولا كفشل مؤكَّد)، ويُحدَّث `getBootstrapData` بأمان في
  الخلفية للتحقق من الحالة الفعلية.
- **تعطيل مُوجَّه**: `busy()` تعطّل فقط الزر أو النموذج الذي نفّذ العملية
  (`state.activeTrigger`، يُضبط في موزّع الأحداث)، لا كل أزرار النظام —
  ويُفكّ التعطيل دائمًا عبر `.finally()` بصرف النظر عن النجاح أو الفشل أو
  انتهاء المهلة.
- **معرّفات عمليات (opId)** للعمليات الحساسة القابلة للتكرار عند إعادة
  المحاولة (إنشاء جمعية/مندوب، قبول طلب انضمام، تأكيد تسليم) — الخادم
  (`withIdempotency_` في `DataUtils.gs`) يُعيد نفس نتيجة المحاولة الأولى
  الناجحة حرفيًا بدل تكرار الإنشاء أو رفض إعادة المحاولة برسالة مربكة.
- **استجابات جزئية بعد الحفظ**: `saveBeneficiary`/`saveDevice`/
  `saveDelegate`/`saveAssociation`/`assignDelegate`/`confirmDelivery`/
  `updateDeliveryStatus`/`saveActivity`/`updateAssociationSettings`/
  `reviewAssociationApplication` لم تعد تُعيد `getBootstrapData` كاملة —
  فقط السجل المعدَّل (`record`) وملخّصًا مصغَّرًا (`summary`) تدمجهما
  الواجهة محليًا (`upsertRecord`/`mergeSummary`) بدل استبدال كل البيانات.
- **تحميل عند الفتح لا عند الدخول**: سجل العمليات (`listAuditLog`)،
  الأنشطة والمراحل والشواهد (`getActivitiesBundle`)، وطلبات الانضمام
  (`listApplications`) لم تعد ضمن `getBootstrapData` الأولي — تُجلب فقط
  عند فتح صفحتها، مُرقَّمة، ببحث وفلترة خادميين حقيقيين. لوحة البيانات
  تعرض معاينة صغيرة ثابتة (10 سطور) من سجل العمليات فقط، لا السجل كاملًا.
- **ترقيم خادمي عام** (`Pagination.gs`): `listBeneficiaries` (مُدمَجة
  بالكامل في صفحة المستفيدين) و`listAuditLog`/`listApplications` (مُدمَجتان
  في صفحتيهما) تدعم صفحة/حجم صفحة/بحث/فلترة/ترتيب، مع فرض عزل الجمعيات من
  الخادم دائمًا. `listDevices`/`listAssociations`/`listDelegates` جاهزة
  ومختبَرة خادميًا لكن دمجها في واجهة الجداول المقابلة (التي لا تزال تُحمَّل
  كاملة ضمن Bootstrap لأسباب موثَّقة في `HANDOFF.md`) عمل متبقٍ.
- **قياس منظَّم**: `perfTime_`/عدّادات `_PERF_` (`DataUtils.gs`) تطبع سطر
  JSON واحدًا (اسم العملية، الزمن، عدد القراءات/الكتابات — بلا أي بيانات
  حساسة) في سجل التنفيذ (Executions) لكل: دخول، Bootstrap، بحث/ترقيم،
  حفظ، تعيين مندوب، تأكيد تسليم.
- **`tools/perf-scale-test.js`**: تقرير أداء بأحجام محاكاة 100/1000/5000
  مستفيد داخل Node.js فقط (بلا أي اتصال حي). راجع `RELEASE.md` لنتائجه
  الكاملة والتفريق الصريح بين زمن التنفيذ المحلي وزمن شبكة Apps Script
  الحقيقي غير المتاح قياسه من هذه البيئة.
- **`Index.html` بقي ملفًا واحدًا عمدًا في هذه المرحلة أيضًا** — نفس
  التبرير التقني من مرحلة إعادة الهندسة الأولى (`HtmlService.include`
  يُدمَج نصيًا على الخادم قبل الإرسال، فلا يقلّل الحمولة الفعلية، ويزيد
  خطر أعطال حدود الملفات في نطاق JS عام مشترك).

## الموقع الجغرافي وأدوات المندوب (المرحلة الخامسة)

- **اختيار الموقع بصريًا بلا مفتاح API**: Leaflet.js + بلاطات
  OpenStreetMap — مجانيان بالكامل، يُحمَّلان فقط عند فتح نموذج إضافة/تعديل
  مستفيد (`initLocationPicker`)، بمهلة تحميل صريحة (6 ثوانٍ) وسقوط آمن
  كامل عند الفشل: تبقى حقول العنوان والإدخال اليدوي لخط العرض/الطول وزرا
  "استخدم موقعي الحالي"/"فتح في خرائط جوجل" تعمل جميعًا بلا أي اعتماد على
  نجاح تحميل الخريطة.
- **الإحداثيات أرقام حقيقية في الخادم دائمًا**: `optionalCoordinate_`
  (`Validation.gs`) نطاق عالمي قياسي (خط العرض -90..90، خط الطول
  -180..180)، ترفض NaN/Infinity، وترفض طرفًا واحدًا من الزوج بلا الآخر
  صراحة — لا اعتماد على تحقق الواجهة فقط أبدًا.
- **بيانات موقع موحَّدة**: المنطقة، المدينة، العنوان، "علامة مميزة"
  اختيارية، خط العرض/الطول، "مصدر الموقع" (خريطة/الموقع الحالي/استيراد/
  يدوي)، و"تاريخ تحديث الموقع" — كلها أعمدة مستقلة في ورقة "المستفيدون"،
  تُحدَّث فقط عند تغيّر الإحداثيات فعليًا، لا عند أي تعديل آخر.
- **الاستيراد الجماعي**: خط العرض/الطول اختياريان (يجب وجودهما معًا أو
  غيابهما معًا)، Excel يقبل أيضًا مرادفات إنجليزية (`Latitude`/`Longitude`)
  وعمود "العلامة المميزة" الاختياري، ومعاينة حقيقية قبل الاعتماد تعرض رقم
  كل صف وسبب رفضه والإحداثيات المقروءة — **الصفوف الخاطئة لا تُستورَد
  إطلاقًا**، فقط الصحيحة.
- **أدوات المندوب**: زر اتصال (`tel:` + بديل نسخ تلقائي عند الحجب)، زر
  "نسخ الرقم" صريح دائم الظهور، واتساب بصيغة دولية صحيحة، وزر موقع محروس
  (لا يفتح رابطًا فارغًا أبدًا — تنبيه واضح إن لم توجد إحداثيات ولا عنوان).
- **مسار اليوم**: ترتيب "أقرب جار" بصيغة Haversine (مجاني بالكامل، **مسافة
  تقريبية بخط مستقيم فقط، لا توجيهًا مروريًا فعليًا** — موضَّح صراحة في
  الواجهة)، مستفيدون بلا إحداثيات في قسم منفصل بأزرار تواصل كاملة (لا
  استبعاد)، وتحديث حالة كل محطة فور تأكيد التسليم أو تسجيل تعذّره دون
  إعادة حساب المسار أو تحميل الصفحة بالكامل.
- **الخصوصية**: إذن الموقع يُطلَب فقط بضغط المستخدم على زر صريح (لا عند
  الدخول ولا تلقائيًا)، ولا تُسجَّل أي إحداثيات حيّة للمندوب في سجل
  العمليات أو التسليمات.

## قواعد لا تُخالَف

- لا تُشغّل `setupSheets_(token)` على ملف يحتوي بيانات إنتاجية فعلية دون
  تأكّد — آمنة ومتكررة (لا تحذف ولا تكرر بيانات) لكنها خطوة يجب أن تكون
  واعية. **كل دوال الإعداد/الترحيل/التشخيص أصبحت خاصة (`_`) ومقفلة خلف رمز
  وصول صيانة مؤقت** — راجع `DEPLOYMENT.md` القسم 5 و`SECURITY_REVIEW.md`
  القسم 2 قبل أي تشغيل.
- لا تُغيّر عناوين أعمدة Google Sheets؛ الكود يقرأ بالاسم العربي حرفيًا.
- لا تُعِد تسمية `Index.html`؛ `doGet` يستدعيه بالاسم `'Index'`.
- لا تضع أي سر أو مفتاح داخل `Index.html` — الملف يصل إلى المتصفح كاملًا.
- لا تُشغّل أي دالة ترحيل (`migrateReferenceData_`, `migratePhoneNumbers_`,
  `migrateLegacyReferenceValues_`) على نسخة إنتاجية دون تشغيل نسخة المعاينة
  القابلة للقراءة أولًا حين تتوفر (`previewPhoneNormalization_` قبل
  `migratePhoneNumbers_`، أو `diagnoseReferenceDataIssues_`/
  `migrateLegacyReferenceValues_(token, true)` قبل `migrateLegacyReferenceValues_(token, false)`).

## التثبيت والتشغيل داخل Google Apps Script (من الصفر)

1. أنشئ Google Sheet جديدًا فارغًا (سيكون قاعدة البيانات).
2. من القائمة: الإضافات ← Apps Script (أو Extensions ← Apps Script).
   سيُفتح محرر Apps Script مرتبطًا تلقائيًا بهذا الملف.
3. احذف محتوى `Code.gs` الافتراضي (الملف الفارغ الذي ينشئه Apps Script
   تلقائيًا). لكل ملف من ملفات `.gs` الستة عشر في هذا المستودع
   (`Config.gs`، `ReferenceData.gs`، `Auth.gs`، `Bootstrap.gs`،
   `Beneficiaries.gs`، `Delegates.gs`، `DevicesAssociations.gs`،
   `Applications.gs`، `ExecutionTracking.gs`، `StateRules.gs`، `Pagination.gs`،
   `Normalize.gs`، `DataUtils.gs`، `Validation.gs`): أضف ملف Script جديدًا بنفس الاسم
   (بلا امتداد `.gs` عند التسمية داخل المحرر — يضيفه Apps Script
   تلقائيًا) والصق فيه محتوى الملف المقابل من هذا المستودع كاملًا
   حرفيًا. **لا يهم ترتيب الإضافة** — Apps Script يدمج كل ملفات `.gs`
   ضمن نطاق عام واحد بصرف النظر عن اسم الملف أو ترتيبه.
4. من القائمة الجانبية في المحرر: أضف ملفًا جديدًا من نوع **HTML** باسم
   `Index` بالضبط (بلا امتداد `.html` في اسم الملف داخل المحرر — Apps
   Script يضيفه تلقائيًا). الصق فيه محتوى `Index.html` من هذا المستودع كاملًا.
5. احفظ المشروع (Ctrl/Cmd + S).
6. من قائمة الدوال أعلى المحرر اختر `setupSheets`، ثم اضغط ▶ تشغيل.
   في أول تشغيل سيطلب منك Google صلاحيات الوصول — وافق عليها (المشروع
   يطلب فقط صلاحية Google Sheets الخاصة بالملف نفسه).
7. افتح **سجل التنفيذ** (Executions، الأيقونة الشبيهة بالساعة على
   الشريط الجانبي الأيسر، وليست أدوات المطوّر F12 في المتصفح) وابحث عن
   السطر الذي يحتوي `بيانات المدير المؤقتة`. سيظهر بريد إلكتروني وكلمة
   مرور مؤقتة لأول حساب مدير — سجّل الدخول بهما فورًا ثم غيّر كلمة
   المرور من صفحة الإعدادات داخل النظام نفسه.
8. **النشر كتطبيق ويب**: من القائمة أعلى يمين المحرر اضغط **Deploy /
   نشر** ← **New deployment / نشر جديد** ← اختر النوع **Web app / تطبيق
   ويب**. اضبط:
   - Execute as: **Me / أنا** (صاحب المشروع).
   - Who has access: **Anyone / أي شخص** (ليتمكن أعضاء الجمعيات
     والمناديب من الدخول من خارج حساب Google الخاص بك؛ الوصول الفعلي
     محكوم بالكامل من داخل النظام عبر الأدوار وكلمات المرور، وليس عبر
     صلاحيات Google).
   - اضغط **Deploy / نشر**، ثم انسخ رابط تطبيق الويب الناتج وشاركه مع
     المستخدمين.
9. لأي تحديث لاحق على أي ملف `.gs` أو على `Index.html`: كرّر النشر عبر
   **Manage deployments / إدارة النشرات** ← تعديل النشرة القائمة ← إصدار
   جديد، بدل إنشاء نشرة جديدة، حتى يبقى الرابط نفسه ثابتًا لدى المستخدمين.

## تحديث نسخة قائمة فعليًا (وليس تثبيتًا من الصفر)

1. من الفرع `claude/code-index-review-kz5k4u` في هذا المستودع، انسخ محتوى
   كل ملف `.gs` الستة عشر و`Index.html` والصقها فوق نظيراتها القائمة في
   محرر Apps Script (استبدال كامل لكل ملف، لا دمج يدوي جزئي). إن كانت
   نسختك الحية لا تزال بملف `Code.gs` واحد قديم من قبل هذا التقسيم:
   احذفه بعد لصق الملفات الستة عشر الجديدة والتأكد من نجاح `setupSheets`،
   لا قبل ذلك.
2. شغّل الفحوص محليًا (`node tools/verify.js` وما يليها) على
   نفس النسخة قبل اللصق للتأكد من عدم وجود كسر إن كنت عدّلت شيئًا يدويًا.
3. الميزات الإضافية الجديدة (طلبات الانضمام، المصادر المرجعية، عمودا
   الموقع الجغرافي وأعمدة "علامة مميزة"/"مصدر الموقع"/"تاريخ تحديث
   الموقع" في ورقة المستفيدين، أعمدة "يجب تغيير كلمة المرور" وكلمة
   المرور/الرمز السابقَين في ورقة المستخدمين) تُنشئ أوراقًا أو أعمدة جديدة
   تلقائيًا فقط عند تشغيل `setupSheets` — وهي إضافية بالكامل ولا تمس أي
   عمود أو صف موجود في الأوراق الحالية. شغّلها مرة واحدة بعد كل تحديث
   يضيف ورقة أو عمودًا جديدًا.
4. أعد النشر عبر **Manage deployments ← New version** كما في الخطوة 9 أعلاه.

انظر `HANDOFF.md` لحالة المشروع التفصيلية الحالية: ما المكتمل والمختبر،
وما المتبقي، وأي ترحيل مكتوب لكنه غير مُشغَّل بعد. انظر `RELEASE.md` لخطة
اختبار حي كاملة خطوة بخطوة قبل أي نشر واسع، تشمل بيانات اختبار وهمية

## ملاحظات معمارية مهمة (المرحلة التاسعة)

### نطاق الطلب الواحد

`_TABLE_CACHE_` في `DataUtils.gs` **محصورة بالطلب الواحد** ولا تعبره
إطلاقًا. تُمسح صراحةً في `beginRequest_` المستدعاة من `requireSession_`
(بوابة كل دالة محروسة) ومن نقاط الدخول العامة (`login`،
`submitAssociationApplication`).

السبب: Apps Script يُبقي المتغيّرات العامة حيّة بين التنفيذات داخل نفس
الـwarm isolate، وقد يخدم تنفيذات متزامنة من isolates متعددة. الاعتماد
السابق على TTL زمني كان يسمح لكتابة في isolate بألّا تُبطل نسخة isolate
آخر، فتعود قائمة أحيانًا بحالة ما قبل الكتابة.

**قاعدة صيانة:** لا تستدعِ دالة عامة من داخل دالة عامة أخرى — استخدم
النسخة الداخلية (`listBeneficiaries_`، `getBootstrapDataFor_` …) التي
تأخذ المستخدم المُتحقَّق منه. الاستدعاء المتداخل يُعيد بدء الطلب في
منتصفه فيمسح الذاكرة ويُعيد قراءة الأوراق بلا داعٍ. **عمدًا لا يوجد
عدّاد عمق** يحمي من ذلك: عدّاد كهذا يجب أن يُوازَن في كل مسار (بما فيه
مسارات الاستثناءات)، وأي اختلال واحد يُجمّد المسح إلى الأبد داخل warm
isolate — وهو بالضبط العطل الذي يمنعه هذا التصميم.

### المصادر المرجعية

`getReferenceData()` تُعيد القائمة المعتمدة **المضمَّنة في الكود** حين
تكون ورقة «البيانات المرجعية» غير موجودة أو فارغة (`source:'builtin'`)،
والورقة — متى عُبِّئت — تتجاوزها بالكامل (`source:'sheet'`). لذلك تعمل
القوائم المنسدلة المترابطة فورًا **بلا أي ترحيل ولا كتابة في الملف
الحي**. التحقق في الخادم صارم، مع استثناء واحد موثَّق: قيمة مخزَّنة
مسبقًا في السجل نفسه تُقبل كما هي (`isGrandfatheredValue_`) حتى لا تمنع
قيمة قديمة تعديلَ حقل آخر تمامًا.

### قياس الأداء

كل استجابة كائنية تحمل `_meta = {traceId, op, serverMs, reads, writes}`
عبر `withMeta_`. لا يحتوي أي رمز جلسة ولا كلمة مرور ولا تجزئة ولا ملح
(مُختبَر في `tools/security-test.js` القسم 13). للمقارنة قبل/بعد:
`node tools/perf-phase-bench.js`.
