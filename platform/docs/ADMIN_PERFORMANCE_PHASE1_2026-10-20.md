# تحسين أداء الإدارة — الدفعة الأولى، 2026-10-20

## الحالة والنطاق

تنفيذ محلي على `codex/admin-performance-20261020`، بعد الأساس `110792f`.
لم يُنشر ولم تُعدّل بيانات الإنتاج أو قرارات الأهلية أو التقييم أو الإشعارات.
الفرع يرث تطوير أبانمي السابق؛ يجب مراجعة فرق الإصدار الكامل قبل النشر، لا هذه الدفعة وحدها.

## ما تغيّر

- فهرس مصغّر واحد للطلبات بدل أربع صفحات API لتحميل 319 طلبًا. قائمة الملفات لا تحمل إجابات الطلب أو ماليته أو أدلته؛ يُقرأ الملف الكامل حديثًا عند فتحه.
- تبقى المرشحات والترتيب على المجموعة الكاملة المسموح بها، لا الصفحة المعروضة فقط. الفهرس محدود بـ5000 طلب، ويرفض التجاوز بدل إظهار مجموعة ناقصة. هذا ليس ترقيمًا خادميًا نهائيًا.
- دمج قراءة الأهلية والأدلة الحالية في قراءة تفصيلية واحدة، مع بقاء التحقق الأصلي عند الحفظ.
- تحديث الصفوف المتأثرة بعد الإجراءات عبر إسقاط مختصر بدل إعادة الملف الكامل، مع حماية الطلبات المتأخرة والملغاة واختلاف الحساب/النطاق.
- تداخل القراءات المستقلة لإشعارات الاختيار والمشاركة دون تغيير قواعد قابلية الاختيار أو الإشعار.
- تشغيل قراءات لوحة الإدارة المستقلة بتزامن محدود إلى اثنتين لكل طلب، بدل تسع قراءات متسلسلة. ليس حدًا عالميًا لاتصالات جميع المستخدمين ولا لقطة معاملات موحدة.
- صلاحيات الإدارة وحدود المناطق باقية؛ المسارات الجديدة خاصة وغير قابلة للتخزين المشترك. لا تغييرات على المصادقة أو RLS أو مخطط البيانات أو مفاتيح الخدمات.

## الفحوص المنجزة

- الخادم: 51 مجموعة، 754 اختبارًا ناجحًا. الواجهة: 102 اختبار ناجح.
- نجاح فحص الأنواع وlint وبناء الإنتاج للخادم والواجهة.
- تنفيذ SQL الفهرس الفعلي ومعاملاته محليًا على PostgreSQL معزول عبر PGlite و319 طلبًا وهميًا: الترتيب، آخر صف، حدود المناطق، رفض النطاق التالف، استبعاد JSON الخاص، عد الإجابات القديمة، وعدم اقتطاع الفهرس.
- تجربة Chrome محلية بواجهة فعلية وAPI وهمي للقراءة فقط: 319 طلبًا و13 صفحة عرض، فرز المجال الذي لا يوجد إلا في الطلب319، ثم فتح ملفه الكامل مرة واحدة. فتح نافذة الأهلية استخدم GET واحدًا مع `view=review`، وفتح التقييم استخدم قراءة الملف الكامل دون حفظ.
- ظهرت قراءتان لفهرس الاختيار عند تركيب المكوّن في وضع التطوير (Strict Mode)؛ ليستا قياس إنتاج. لم يُستخدم زمن الاستجابة الوهمي لتقدير تحسن المنصة الحقيقية.
- خادم الاختبار على loopback فقط، يرفض الكتابة، ولا يستخدم قاعدة بيانات أو أسرارًا. أُوقف بعد التجربة. السكربت: `tools/admin-performance-fixture.cjs`، ويحتاج واجهة تطوير على localhost:3180 ومنفذ3001 فارغًا.

## القياسات السابقة والحدود

في الفحص السابق للإنتاج: تحميل بيانات لوحة الإدارة نحو6.53ث، قائمة الاختيار8.26ث، وقائمة الملفات11.84ث؛ هذه قياسات عينات وليست ضمانات ثابتة. قراءة تفاصيل الأهلية نحو3.9ث. كانت الأدلة والتفاصيل متوازية أصلًا، فلا يصح جمع مدتيهما.

لا توجد نسبة تحسن زمنية مثبتة بعد هذه الدفعة، لأنها لم تُنشر. تقليل أربع قراءات قائمة إلى قراءة واحدة مؤكد في الكود والفحص، لكنه لا يعني تحسن الزمن بنسبة75% ولا زوال كل البطء. فتح ملف من قائمة الملفات صار يتطلب قراءة حديثة بدل الاعتماد على التفاصيل المحمّلة مسبقًا؛ هذا مقابل تقليل التحميل الأولي وحجم البيانات.

## ما بقي من الخطة

1. نشر API قبل الواجهة، والتحقق من توافق الإصدارين. الواجهة الجديدة تحتاج مسار الفهرس و`view=review`؛ عند فشلهما تعرض خطأ، ولا تُخمّن نتائج أو تحفظ بيانات ناقصة. للرجوع: أعد الواجهة القديمة أولًا ثم API القديم؛ API الجديد يحتفظ بالعقد القديم للقائمة والتفاصيل.
2. قياس الإنتاج قبل/بعد بنفس الحساب والنطاق والعمليات، مع مراقبة الأخطاء والحمولة والضغط، دون حفظ قرارات اختبارية.
3. معالجة تكرار `/auth/me` وتسلسل الجلسة بأمان، والاحتفاظ بفهرس صالح عبر التنقل مع إعادة التحقق، وترقيم خادمي كامل عند الحاجة، وتخفيف قائمة المشاركات.
4. إضافة توقيتات خادمية وتحليل SQL/الاتصالات عند توفر وصول موثوق. لا يوجد دليل كافٍ الآن لزيادة pool أو شراء موارد أو إضافة فهارس عشوائية.
