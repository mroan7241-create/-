### Route inventory summary
- **16 routes total.**
- **3 are explicit, self-declared placeholder/dev/shell pages**: `/` (NODE-0 health check), `/dashboard` (NODE-1 minimal shell, literally named `DashboardShellPage`), `/dev/session` (NODE-1 dev-only, explicitly "not linked from any other screen"). All three carry Arabic source comments explicitly disclaiming production status and pointing at `MIGRATION_ROADMAP.md`.
- **13 are real, production-quality business screens** wired to genuine API endpoints (association applications, associations CRUD, beneficiaries + needs review (admin table view + association card view), device inventory, receipt batches create/send/confirm, auth flows). These are not mockups — they implement real business rules client-side (idempotency via `opId`/`clientRequestId`, duplicate-warning handling, damage-photo/item-linking validation, role guards, one-time-secret reveal patterns, session-invalidation confirmations) that closely track the API contracts in `lib/api.ts`.
- One page (`/association/settings`) is real but has a **notable functional gap**: it doesn't fetch/pre-populate existing values.
- No route anywhere renders literal mock arrays or fixture data — all list/detail data comes from `apiFetch`/`apiUpload` calls into the real NestJS API.

## Section 2 — Design System State

**No formal design system / component library exists.** There is no `components/` directory, no Storybook, no design-tokens package, no shared `<Button>`/`<Table>`/`<Modal>` React components. Every page is a single large client component that inlines its own JSX and pulls shared **style objects** (not components) from `apps/web/app/lib/ui.ts`.

- **Styling approach**: 100% inline `style={{...}}` props using `CSSProperties` objects, no CSS Modules, no Tailwind, no styled-components/emotion. `apps/web/app/globals.css` defines only CSS custom properties (color tokens `--zad-*`/`--gold-*`, radii `--r-*`, `--canvas`/`--paper`/`--ink`/`--line`) plus a few bare-element resets (`body`, `h1-h4`, `a`, `code`). The file's own header comment states these tokens were "منقولة حرفيًا من Index.html (الفرع القديم)" (copied literally from the legacy branch's `Index.html`) as an "initial identity reference," and explicitly says the rest of the design (full typography, components) is deliberately *not* migrated yet in NODE-0.
- **Shared style primitives** (`apps/web/app/lib/ui.ts`): `pageStyle`, `narrowPageStyle`, `cardStyle`, `labelStyle`, `inputStyle`, `primaryButtonStyle`, `secondaryButtonStyle`, `dangerButtonStyle`, `tableStyle`/`thStyle`/`tdStyle`, `errorStyle`/`successStyle`/`mutedStyle`/`ltrStyle`, `honeypotWrapperStyle`, `statusBadgeStyle(tone)`, `modalOverlayStyle`/`modalStyle`. These are reused fairly consistently across the 13 real business pages, so there IS a coherent *visual* vocabulary (consistent colors, radii, spacing) even though it's implemented as exported style-object constants rather than components. The file's own comment says these were "extracted from the pattern of existing NODE-0/NODE-1 screens (login/dashboard) so new screens stay on the same Zad identity without inventing a new visual style, and without repeating the same objects in every file."
- **Component reuse**: Only two real shared components exist: `useRoleGuard` (a hook enforcing client-side role redirects, explicitly documented as "convenience only — the real guarantee is `@Roles(...)` on the server") and `AssociationSelect` (a searchable/debounced association picker used by `admin/inventory` and `admin/receipts`). Every modal, table, form, and status badge is duplicated per-page rather than extracted into a component — e.g. the receipt-item detail table markup is nearly identical between `admin/receipts/page.tsx` and `association/receipts/page.tsx` but is copy-pasted, not shared.
- **Inconsistencies observed**: `admin/inventory/page.tsx` and `admin/receipts/page.tsx`/`association/receipts/page.tsx` use plain unstyled `<button>` elements for some controls (e.g. pagination buttons) instead of `secondaryButtonStyle`, unlike the more polished `admin/applications`/`admin/associations`/`admin/beneficiaries` pages — a sign of ad hoc, page-by-page styling discipline rather than enforced consistency.
- **RTL/i18n**: All content is Arabic with `dir="rtl"` set at the `<html>` level in `layout.tsx`; LTR is force-applied per-field (`ltrStyle`) for codes, emails, phone numbers, dates. No i18n library — all strings are hardcoded Arabic literals inline.
- **Verdict**: styling is **consistent-but-ad-hoc** — a real, intentional token system exists (colors/radii/spacing), and it's genuinely reused, but there is no component abstraction layer, so every page re-implements table/modal/form chrome by hand. This is explicitly acknowledged in the source as a deliberate, temporary state pending later NODE phases.

The only "placeholder" hits are legitimate HTML `placeholder=` input attributes (e.g. `"05XXXXXXXX"`, `"MND-XXXXXX"`), and the only "temporary" hits are the legitimate `temporaryPassword` domain field name (the actual one-time password feature, not a stub marker).
