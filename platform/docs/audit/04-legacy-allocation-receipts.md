## Allocation Algorithm (detailed prose)

**Entry point / triggers.** There is **no public endpoint and no scheduled trigger** for allocation. `runAutoAllocation_(associationId, user)` (AutoAllocation.gs:460) is called internally from exactly two places, always **after** another operation has already succeeded and always from **inside a lock already held by the caller**:

1. `ReceiptBatches.gs:564` — inside `confirmReceiptBatch_`, immediately after a receipt batch confirmation writes new "بالمستودع" (in-warehouse) device rows (i.e., clean/undamaged received devices become inventory).
2. `BeneficiaryNeeds.gs:759` and `BeneficiaryNeeds.gs:867` — inside the beneficiary-needs approval/review flow, after new beneficiary needs are approved ("معتمد").

Both call sites already hold `LockService.getScriptLock()` via `runLockedIdempotent_` (DataUtils.gs:482) before calling `runAutoAllocation_`, so the allocation engine **never acquires its own lock** — "same principle as `saveDevice_`/`assignDelegate_`" per the file's own header comment. `runAutoAllocation_` is deliberately fault-isolated: if it throws, the caller catches the error, logs it, and does **not** fail the receipt-confirmation or needs-approval operation that triggered it (see ReceiptBatches.gs:560-568, BeneficiaryNeeds.gs ~759/867).

**Inactive-association guard.** `runAutoAllocation_` re-checks (inside the caller's lock) that the association's status is exactly `'نشطة'` (active); if not, it silently skips (`{ok:true, moved:0, skipped:'inactive-association'}`) rather than throwing, because failure here must never surface as an error for the already-successful triggering operation.

**Algorithm shape — global optimization, not per-association/per-beneficiary greedy, and not cross-association either.** The engine is explicitly scoped to **one association at a time** (`planAutoAllocation_(associationId)` — AutoAllocation.gs:30), so it does **not** pool inventory or beneficiaries across different associations. But *within* a single association, it solves a genuine global optimization problem rather than naive FIFO/sequential per-beneficiary linking:

- It models the problem as a **0/1 knapsack / exact-sum dynamic program** over three device-type dimensions (`ثلاجة` fridge, `فرن` oven, `غسالة` washer — `NEW_NEED_DEVICE_TYPES`). Each candidate beneficiary is one "item" with a `fullCost` vector (which types they need in total, ready+missing) and a `gapCost` vector (which types are still missing).
- The **objective is "maximize the count of beneficiaries who can be fully completed"** in one shot — not simply "assign devices to whoever asks first." The code's own comments (Arabic, translated): *"The decision of who gets completed is a single decision that builds the redistributable resource pool from free warehouse stock AND every device already 'ready' (assigned) to a partially-fulfilled need together — not a free-stock-first-then-greedy-reclaim phase, because that missed globally better solutions."*
- DP state space: 6 dimensions (demand-cap and gap-cap per device type × 3 types), each state tracking exact resource consumption; `dp[z]` = max beneficiaries completable exactly at resource-consumption state `z`. Standard 0/1 knapsack backward iteration prevents reusing the same beneficiary twice.
- **Tie-breaking / selection among equally-good final states** (AutoAllocation.gs:230-248), in strict priority order:
  1. Largest count of fully-completed beneficiaries (primary objective).
  2. Then smallest total remaining "gap" count (fewest missing-device slots left).
  3. Then smallest actual "reclaim" count (fewest devices that would need to be taken back from another beneficiary who already had them "ready").
  4. Then a fixed deterministic order (smallest DP index) as final tie-break.
- **Reclaiming devices**: a device already marked "ready" (خصص/assigned, fulfillment status "جهاز جاهز") for one beneficiary can be reassigned ("استرجاع"/reclaim) to a *different, DP-selected* beneficiary **only if that source beneficiary was not itself selected** in the optimal solution — i.e., reclaiming is reserved strictly for enabling another beneficiary's completion, never used for blind partial redistribution among non-selected beneficiaries (explicit design comment, AutoAllocation.gs:315-317).
- **Beneficiary ordering used only for the leftover/partial phase** (not the core DP): beneficiaries who were *not* selected by the DP (couldn't be fully completed) still get a best-effort partial allocation from any **remaining free warehouse stock only** (no reclaiming), ordered by: fewest missing needs first (closest to completion), then beneficiary ID ascending on ties (AutoAllocation.gs:92-96, explicitly documented as "a fixed technical ordering, not FIFO or business priority").
- **No association-priority, no submission-date/FIFO ordering** is used anywhere in the selection logic itself — the code explicitly disclaims this ("لا أولوية تجارية ولا FIFO" / "no business priority and no FIFO").

**What is read (state snapshot).** `planAutoAllocation_` is a **pure, side-effect-free planning function** — it reads (via `readTable_`, which is a per-request cache so all reads inside one lock session see one consistent snapshot):
- `beneficiaries` sheet — candidates filtered to: same association, beneficiary-review status = "معتمد" (approved), beneficiary status ≠ "ملغي" (not canceled), delivery status ≠ "تم التسليم" (not already delivered).
- `beneficiaryNeeds` sheet — approved needs ("حالة القرار" = "معتمد") for the association.
- `devices` sheet — to (a) map each need to its currently linked device (if any), (b) build the free-warehouse pool (`حالة الجهاز` = "بالمستودع", same association, unassigned), and (c) build the "ready-for-reclaim" pool (devices in state "مخصص" linked to a need whose fulfillment is "جهاز جاهز").
- `associations` sheet — active-status check.

**Custody-started exclusion (hard skip, whole beneficiary).** A beneficiary is entirely excluded from the run if **any** of their needs already has a fulfillment status indicating real custody has started: `'معيّن للمندوب — بانتظار التنفيذ'`, `'خرج مع المندوب'`, `'مؤجل'`, `'بانتظار تأكيد الإرجاع'`, `'أعيد للجمعية/المستودع'`, `'تم التسليم'` (constant `AUTO_ALLOCATION_CUSTODY_STARTED_`, AutoAllocation.gs:16-18). This beneficiary/needs are "never touched" by the engine at all.

**Data-integrity guard (fail-fast, no partial plan).** If a need is in fulfillment state "جهاز جاهز" (device ready) or "بانتظار تعيين مندوب" (awaiting delegate assignment) but does **not** have exactly one valid linked device (matching type, association, beneficiary, and device status "مخصص"), or if more than one device is linked to the same need, `planAutoAllocation_` throws immediately — **no partial plan is ever produced**. This mirrors the same invariant used in `planNeedTransitionsForDeviceChange_` in BeneficiaryNeeds.gs.

**What is written (single transaction).** After planning, `validateAutoAllocationPlan_` (AutoAllocation.gs:348) re-validates every planned need transition through the same `StateRules`-style assertion functions used elsewhere (`assertDeviceLinkFulfillment_`, `assertDeviceUnlinkFulfillment_`, `assertGroupCompletionFulfillment_`, `assertLinkAndGroupCompleteFulfillment_`), and rejects any plan with conflicting double-writes to the same need or device, or any need that would end in "جهاز جاهز"/"بانتظار تعيين مندوب" without an actual linked device — **all before any write happens**. Then `commitAutoAllocationPlan_` (AutoAllocation.gs:392) writes:
1. All `beneficiaryNeeds` fulfillment-status transitions first.
2. All `devices` row updates (beneficiary ID, need ID, status → "مخصص") second.
3. `clearDashboardCache()`.
4. One `audit_()` log row per device move (action "تخصيص تلقائي" for a fresh assignment, "إعادة موازنة تخصيص تلقائي" for a reclaim), isolated so an audit-logging failure never undoes/fails the already-committed allocation.

**Rollback on write failure.** If any write in the commit step throws, the code attempts a best-effort compensating rollback of every row it had *attempted* to write (using pre-write snapshots captured before the try block), and if the rollback itself partially fails, it logs a `traceId` and throws an error demanding manual review — same pattern used by `commitDeviceWithNeed_`/`reviewBeneficiaryNeeds_` elsewhere in the codebase.

**Concurrency / locking model.** `AutoAllocation.gs` itself never calls `LockService`. It is always executed while the caller (`createReceiptBatch`/`sendReceiptBatch`/`confirmReceiptBatch` in ReceiptBatches.gs, or the beneficiary-needs approval endpoints in BeneficiaryNeeds.gs) holds the single global `LockService.getScriptLock()` acquired via `runLockedIdempotent_(operationScope, actorId, opId, fn)` (DataUtils.gs:482), which does `lock.waitLock(15000)` then `fn()` then `lock.releaseLock()` in a `finally`. Because Apps Script's `LockService.getScriptLock()` is a single script-wide lock, **only one mutating operation of any kind (receipt confirmation, needs approval, allocation, device edit, etc.) can run at a time across the whole script**, which is what prevents concurrent allocation runs from corrupting shared inventory state. There is no per-association or per-resource lock — it's a single coarse-grained global mutex with a 15-second wait timeout. `runLockedIdempotent_` additionally supports an idempotency key (`opId`) cached for 300 seconds so a retried request with the same `opId` replays the cached result instead of re-executing.

**Performance guard / abort condition.** Before running the DP, the code computes `totalStates * dpItems.length` and throws (aborting the whole run, no partial write) if it exceeds 4,000,000 — an explicit safety valve against runaway DP state-space size for large batches, described as "rare in practice for a single batch size." No fallback to a suboptimal solution is permitted; it fails closed and requires manual intervention or batch-splitting.

## Summary of what "ExecutionTracking.gs" actually audits

Despite its name suggesting an allocation-run execution log, this file has nothing to do with allocation runs. It is the project-management/activities-tracking + dashboard/alerts + account-settings module. No allocation-run start/end/result audit trail exists anywhere in the seven audited files — the only per-run trace is the generic per-device `audit_()` row written by `commitAutoAllocationPlan_` (ALLOC-010) plus `Logger.log` warnings for isolated internal failures, which are not queryable/visible through any read endpoint in these files.
