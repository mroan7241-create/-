## State Machine (StateRules.gs — authoritative)

StateRules.gs is explicitly documented as "the single central source for status-transition rules" — every function elsewhere that changes a device or delivery status MUST go through `assertDeviceTransition_`/`assertDeliveryTransition_` (etc.) rather than writing the field directly, specifically to prevent transition rules from diverging across files.

**Universal design rule:** self-loops (state → itself) are allowed ONLY where explicitly listed. Terminal states never have an implicit self-loop shortcut — re-confirming an already-completed operation (e.g. re-delivering something already delivered) is always rejected rather than silently accepted as a no-op. Unknown/malformed current or target status values are always rejected explicitly rather than assumed valid (protects against corrupted legacy data).

### 1. Device status (`DEVICE_STATUSES`, physical unit lifecycle)

Values: `بالمستودع` (in warehouse) → `مخصص` (allocated) → `مع المندوب` (with delegate) → `تم التسليم` (delivered); `تالف` (damaged) reachable from any non-terminal state.

| From | Allowed To | Guard / Trigger |
|------|-----------|------|
| بالمستودع (warehouse) | بالمستودع (self), مخصص (allocated), تالف (damaged) | `linkDeviceToNeed_`/`commitDeviceWithNeed_` allocates on valid link |
| مخصص (allocated) | مخصص (self), بالمستودع (back to warehouse), مع المندوب (with delegate), تالف (damaged) | unlink returns to warehouse; delegate pickup (future endpoint) moves to "with delegate" |
| مع المندوب (with delegate) | مع المندوب (self), مخصص (back), تم التسليم (delivered), تالف (damaged) | delivery confirmation; can also be pulled back to "allocated" |
| تم التسليم (delivered) | *(none — terminal, no self-loop)* | re-confirming a completed delivery is always rejected |
| تالف (damaged) | تالف (self), بالمستودع (repaired/returned to warehouse) | manual recovery path |

Enforced by `assertDeviceTransition_` (StateRules.gs:55-66). Unknown target status or unknown current status both throw explicitly. A brand-new device (`fromStatus` empty) is allowed any initial status (checked elsewhere by the caller).

### 2. Beneficiary delivery status (`DELIVERY_STATUSES`)

Values: `لم يبدأ` (not started) → `جاري التجهيز` (being prepared) → `خرج مع المندوب` (dispatched with delegate) → `تم التسليم` (delivered); `تعذر التسليم` (delivery failed) as a retry loop.

| From | Allowed To | Guard / Trigger |
|------|-----------|------|
| لم يبدأ (not started) | لم يبدأ (self), جاري التجهيز (being prepared), خرج مع المندوب (dispatched) | `assignDelegate_` sets to "being prepared" only (per Phase 2.3 correction — it does NOT jump straight to "dispatched") |
| جاري التجهيز (being prepared) | جاري التجهيز (self), خرج مع المندوب (dispatched), لم يبدأ (back to not-started) | actual pickup (future endpoint) advances to "dispatched" |
| خرج مع المندوب (dispatched) | خرج مع المندوب (self), تم التسليم (delivered), تعذر التسليم (delivery failed) | delivery confirmation or failure |
| تعذر التسليم (delivery failed) | تعذر التسليم (self), خرج مع المندوب (retry dispatch), جاري التجهيز (back to preparing) | retry path |
| تم التسليم (delivered) | *(none — terminal, no self-loop)* | |

Enforced by `assertDeliveryTransition_` (StateRules.gs:69-80). Note: as of the current code, `assignDelegate` is the ONLY beneficiary-domain function in these 4 files that drives this state machine, and it only ever performs `لم يبدأ → جاري التجهيز` (or a same-state self-loop for re-assignment) — the later stages (dispatched/delivered/failed) require a not-yet-implemented pickup/delivery-confirmation endpoint (explicitly called out as intentionally missing — "Phase 3").

### 3. Beneficiary review status (`BENEFICIARY_REVIEW_STATUSES`) — THE beneficiary approval workflow

Values: `تحت المراجعة` (under review) → `معتمد` (approved) | `مرفوض` (rejected) — both terminal, no return path.

| From | Allowed To | Guard / Trigger |
|------|-----------|------|
| تحت المراجعة (under review) | تحت المراجعة (self), معتمد (approved), مرفوض (rejected) | `reviewBeneficiaryNeeds_` (ADMIN only) makes the final call; `setBeneficiaryNeeds_` can (re-)enter this state if needs are added before a final decision |
| معتمد (approved) | *(none — terminal)* | re-approving is rejected |
| مرفوض (rejected) | *(none — terminal)* | re-rejecting is rejected |

Enforced by `assertBeneficiaryReviewTransition_` (StateRules.gs:276-287). This is the definitive "review under → approved/rejected" workflow the audit brief asked about. **Only ADMIN** can trigger the approved/rejected transition (`reviewBeneficiaryNeeds`/`bulkReviewBeneficiaries`, both `requireSession_(token, ['ADMIN'])`). ASSOCIATION can only create/edit while `تحت المراجعة`.

### 4. Need decision status (`NEED_DECISION_STATUSES`) — per individual need/device-type request

Values: `بانتظار المراجعة` (pending review) → `معتمد` (approved) | `مرفوض` (rejected) — both terminal.

| From | Allowed To | Guard / Trigger |
|------|-----------|------|
| بانتظار المراجعة (pending) | بانتظار المراجعة (self), معتمد (approved), مرفوض (rejected) | `reviewBeneficiaryNeeds_` decides each need individually within the combined beneficiary+needs review call |
| معتمد (approved) | معتمد (self only) | re-deciding an already-decided need is rejected |
| مرفوض (rejected) | مرفوض (self only) | same |

Enforced by `assertNeedDecisionTransition_` (StateRules.gs:290-301). Independent per-need — a beneficiary's needs can have mixed approved/rejected outcomes (except: if the beneficiary itself is rejected, ALL its pending needs are force-rejected together with the shared beneficiary reject reason).

### 5. Need fulfillment status (`NEED_FULFILLMENT_STATUSES`) — post-approval device lifecycle for one entitlement

Values (9, in intended progression order): `استحقاق معتمد` (approved entitlement) → `بانتظار توفر الجهاز` (awaiting device availability) → `جهاز جاهز` (device ready) → `بانتظار تعيين مندوب` (awaiting delegate assignment) → `معيّن للمندوب — بانتظار التنفيذ` (assigned to delegate, awaiting execution) → `خرج مع المندوب` (out with delegate) → {`مؤجل` (deferred) | `بانتظار تأكيد الإرجاع` (awaiting return confirmation)} → `تم التسليم` (delivered) / `أعيد للجمعية/المستودع` (returned to association/warehouse).

Full raw transition table (`NEED_FULFILLMENT_TRANSITIONS_`, StateRules.gs:253-273):

| From | Allowed To |
|------|-----------|
| استحقاق معتمد (approved entitlement) | استحقاق معتمد (self), بانتظار توفر الجهاز (awaiting device) |
| بانتظار توفر الجهاز (awaiting device) | بانتظار توفر الجهاز (self), جهاز جاهز (device ready) |
| جهاز جاهز (device ready) | جهاز جاهز (self), بانتظار تعيين مندوب (awaiting delegate assign), بانتظار توفر الجهاز (regress — device unlinked) |
| بانتظار تعيين مندوب (awaiting delegate assign) | بانتظار تعيين مندوب (self), معيّن للمندوب — بانتظار التنفيذ (assigned), بانتظار توفر الجهاز (regress via unlink), جهاز جاهز (regress via group-completion loss) |
| معيّن للمندوب — بانتظار التنفيذ (assigned, awaiting execution) | معيّن للمندوب — بانتظار التنفيذ (self), خرج مع المندوب (out with delegate) |
| خرج مع المندوب (out with delegate) | خرج مع المندوب (self), تم التسليم (delivered), مؤجل (deferred), بانتظار تأكيد الإرجاع (awaiting return confirmation) |
| مؤجل (deferred) | مؤجل (self), خرج مع المندوب (back out with delegate) |
| بانتظار تأكيد الإرجاع (awaiting return confirmation) | بانتظار تأكيد الإرجاع (self), أعيد للجمعية/المستودع (returned) |
| أعيد للجمعية/المستودع (returned to association/warehouse) | أعيد للجمعية/المستودع (self), بانتظار تعيين مندوب (re-enter assignment queue) |
| تم التسليم (delivered) | *(none — terminal)* |

Enforced generically by `assertNeedFulfillmentTransition_` (StateRules.gs:304-315), but StateRules.gs additionally provides **named, restricted "explicit path" wrappers** so that no caller can chain arbitrary hops that are individually legal but never intended together (a documented fix for a prior general BFS-search approach that was removed for being too permissive):

- `assertDeviceLinkFulfillment_` (StateRules.gs:350-356) — device-linking path: `استحقاق معتمد → بانتظار توفر الجهاز → جهاز جاهز`, or `بانتظار توفر الجهاز → جهاز جاهز`, or self-loop at `جهاز جاهز`. No other starting state permitted.
- `assertGroupCompletionFulfillment_` (StateRules.gs:359-364) — one hop only, `جهاز جاهز → بانتظار تعيين مندوب`, when the beneficiary's *entire* approved-needs group becomes simultaneously ready.
- `assertLinkAndGroupCompleteFulfillment_` (StateRules.gs:371-377) — composite: link path immediately followed by group-completion hop, for when linking the last outstanding device completes the whole group in one write.
- `assertGroupRegressionFulfillment_` (StateRules.gs:385-390) — one hop only, `بانتظار تعيين مندوب → جهاز جاهز`, when a sibling need's device gets unlinked and the group loses collective readiness (never applies to a need that's already progressed past assignment).
- `assertDeviceUnlinkFulfillment_` (StateRules.gs:393-398) — unlink path: only from `جهاز جاهز` or `بانتظار تعيين مندوب`, always to `بانتظار توفر الجهاز`.
- `assertDelegateAssignFulfillment_` (StateRules.gs:405-411) — delegate-assignment path (used by `assignDelegate_`, BEN-015): from `جهاز جاهز`, `بانتظار تعيين مندوب`, or self-loop at `معيّن للمندوب — بانتظار التنفيذ`, always to `معيّن للمندوب — بانتظار التنفيذ`.

`assertNeedFulfillmentPath_` (StateRules.gs:327-338) is the shared engine underlying all named wrappers: it requires the caller to supply the *entire intended path* explicitly (never searches for one), and validates every hop against `assertNeedFulfillmentTransition_` in sequence.

### 6. Device receipt-batch status (`RECEIPT_BATCH_STATUSES`) — Phase 3.1, device receiving/reconciliation (adjacent system, mentioned for completeness)

Values: `مسودة` (draft) → `بانتظار تأكيد الجمعية` (awaiting association confirmation) → `تم الاستلام كاملًا` (received complete) | `تم الاستلام مع فروقات` (received with discrepancies).

| From | Allowed To |
|------|-----------|
| مسودة (draft) | بانتظار تأكيد الجمعية (submit for confirmation) |
| بانتظار تأكيد الجمعية (awaiting confirmation) | تم الاستلام كاملًا (received complete), تم الاستلام مع فروقات (received with discrepancies) |
| تم الاستلام كاملًا (received complete) | *(none — terminal)* |
| تم الاستلام مع فروقات (received with discrepancies) | *(none — terminal)* |

Enforced by `assertReceiptBatchTransition_` (StateRules.gs:429-440). Only ADMIN creates a draft; only the association confirms it (once, non-repeatable) into one of the two terminal outcomes. No self-loop on ANY state in this table — every transition is strictly forward-progressing; re-confirming an already-confirmed batch is always rejected. (Out of strict scope of "beneficiary needs," but directly adjacent — device batches ultimately populate the `devices` sheet these state machines govern.)

## Flags / Unusual or Contradictory Findings

1. **Duplicate/shadow status field.** `حالة المستفيد` (`BENEFICIARY_STATUSES`: جديد/تحت المراجعة/معتمد/بانتظار الأجهزة/جاري التسليم/تم التسليم/ملغي) still exists as a column and is still read in a couple of places (e.g., `listBeneficiaries_`'s generic `options.filter` fallback at BEN-004, and `diagnoseStateIntegrity_`'s "cancelled beneficiary" check for `status === 'ملغي'`), but per the BeneficiaryNeeds.gs header comment it is no longer written by any live endpoint — the real, authoritative review state is the separate `حالة مراجعة المستفيد` field (`BENEFICIARY_REVIEW_STATUSES`). A value like `'ملغي'` (cancelled) has **no corresponding value or transition anywhere** in `BENEFICIARY_REVIEW_STATUSES` — meaning "cancellation" as a concept appears to be orphaned/unreachable through any current write path in these 4 files. The Node port should treat `حالة المستفيد` as read-only/historical baggage and decide explicitly whether "cancelled" needs to be reintroduced as a first-class state in the new review state machine, since it currently has no way to be set going forward.

2. **`assignDelegate` is named misleadingly relative to its actual scope.** Despite the name, and despite `DELIVERY_STATUSES` containing `خرج مع المندوب`/`تم التسليم`/`تعذر التسليم`, the only delivery-status transition this function ever performs is `لم يبدأ → جاري التجهيز` (or self-loop). The "real" dispatch/pickup/delivery-confirmation endpoints are explicitly documented as intentionally not yet built (Phase 3). Any parity migration needs to confirm whether those endpoints exist in some *other* .gs file not in this batch (e.g., `DevicesAssociations.gs`, referenced but not read here) — if the full delivery lifecycle genuinely has no server endpoint anywhere in the legacy system, that's a functionality gap the new platform would need to originate rather than port.

3. **Two independent "needs sync" mutation paths with different semantics.** `setBeneficiaryNeeds_` (BEN-020) is purely additive/idempotent (never deletes). `updateBeneficiaryWithNeeds_` (BEN-012), when given `deviceTypes`, performs a full diff-and-reconcile (adds AND deletes pending needs not in the new list). Both are reachable from ADMIN/ASSOCIATION and both mutate the same `beneficiaryNeeds` sheet with overlapping preconditions (must be `تحت المراجعة`, can't touch decided needs) but subtly different endpoint contracts. A parity audit of the front-end (Index.html) should confirm which UI flows call which, since a client that assumes "add-only" semantics calling into the diff-and-reconcile path (or vice versa) would produce surprising results.

4. **Deprecated `saveBeneficiary_` still writes the legacy free-text `الاحتياج` field** and is kept alive only for old test scripts (`tools/*-test.js`). It is explicitly documented as unreachable from any public endpoint, so it should almost certainly be excluded entirely from the Node/NestJS port — flagging in case any test-parity work mistakenly tries to replicate its behavior as if it were live.

5. **`bulkReviewBeneficiaries` re-derives association IDs from each item's own result** rather than accepting them as input, and de-duplicates auto-allocation runs per association after the whole batch — worth replicating exactly in the new platform since a naive "loop and call single-review N times" port would trigger the allocation engine N times instead of once per unique association, which is called out in the source as a deliberate performance/consistency fix (Patch 3.2A.1).

6. **Reference-data "grandfathering."** Region/city and social-status validation both silently accept an out-of-list value if — and only if — it exactly matches what the record already had before this edit (`isGrandfatheredValue_`). This is a genuinely load-bearing business rule (prevents old data from becoming un-editable when reference lists tighten) that's easy to lose in a straightforward "validate against enum" reimplementation — the Node port needs an equivalent "unless unchanged from current DB value" escape hatch, not a flat enum check.

7. **`linkDeviceToNeed` has no UI wiring yet** per its own comments ("server helper + integrity tests only... UI wiring comes in a later phase") — confirm with the Node/NestJS team whether this is truly still unused or whether it was wired up in a later, unreviewed version of Index.html before treating it as low-priority for parity.
