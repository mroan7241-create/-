## Prose Detail

### DEV-006 — `saveDevice_` full guardrail summary (DevicesAssociations.gs:75-255)

This is the single most complex function across both files. Full decision tree:

1. Invalidates cached table reads for devices, beneficiaries, beneficiaryNeeds first (forces fresh reads within the lock already held by the caller).
2. Determines `isNew` (no `payload.id`) vs. edit. New devices get IDs via `nextIdsLocked_('DEV', 1)[0]`.
3. If editing a non-existent device ID → throws "device not found."
4. If the existing device's status is `'مع المندوب'` or `'تم التسليم'` (active custody) → routes entirely to `saveDeviceDescriptiveOnly_` (DEV-007); nothing below applies.
5. Validates/normalizes `type` via `validateDeviceType_` (defined in `ReferenceData.gs`, not read in full for this audit).
6. If the device is linked to a need whose fulfillment has progressed past "device ready" and the requested `type` differs from current → hard block (DEV-008), regardless of the device's own status field.
7. Branches on whether `payload.beneficiaryId` is present:
   - **No beneficiary** → DEV-009 warehouse/unlink path.
   - **Beneficiary present** → DEV-010 assignment path, including the "historical record" special case (a device tied to a beneficiary from before the new need-based linking model existed, with no `رقم الاحتياج` value — allowed to keep existing but not to transition status until properly re-linked).
8. All writes are delegated to `commitDeviceWithNeed_` (DEV-011) — `saveDevice_` itself never calls `updateById_`/`appendObject_` on the devices sheet directly (except via that shared commit function).

### Association Application → Association record field mapping (ASSOC-018)

On approval, these fields are copied verbatim from the application row into the new association row: `اسم الجمعية` (name), `التصنيف` (category), `المنطقة` (region), `المدينة` (city), `أرقام التواصل` (phone), `البريد الإلكتروني` (email). New association always starts `الحالة`=`'نشطة'` (active). Notably: `مجال عمل الجمعية` (sector), `رقم الترخيص` (license number), `تاريخ انتهاء الترخيص` (license expiry), the 8 questionnaire answers, and the license file itself are captured on the *application* record but are **not** copied onto the resulting association record — that data appears to live only in the (now-terminal) application row, not on the association entity going forward. This is worth flagging for the migration: if the new platform's Association entity needs license/sector data, it must either pull it from the linked application record or the schema must be extended to store it directly on the association.

### Association record shape (`normalizeAssociation_`, Normalize.gs:38-55)

Fields returned per association: `id`, `name`, `category`, `region`, `city`, `phone`, `email`, `status`, `beneficiaries` (count), `approvedDevices` (= all devices ever linked to this association), `receivedDevices` (devices with status ≠ warehouse), `deliveredDevices` (status = delivered), `delegates` (count), `progress` (delivered/approvedDevices as a rounded percentage, 0 if no devices). These are computed live from the beneficiaries/devices/delegates tables at read time — not stored columns.

### Device record shape (`normalizeDevice_`, Normalize.gs:57-66)

Fields: `id`, `name`, `type`, `associationId`, `beneficiaryId`, `status`, `createdAt` (date only), `deliveredAt` (date+time), `notes`.

## Summary for reporting back

- **~42 distinct features/business rules** extracted across the two files (23 from Applications.gs, 19 from DevicesAssociations.gs), covering: public application submission (with honeypot, idempotency, rate limiting, cross-field validation, license file upload/verification), public status check, admin license-file viewing, admin application list/search, admin accept/reject workflow (with account+association auto-creation on accept), association CRUD (create/update, with account creation and session revocation on deactivation), password reset, and an unusually deep device-assignment state machine tightly coupled to a separate "beneficiary needs" entity.

### Notable / unusual / worth flagging for migration:

1. **No license/sector data survives approval.** The approved association record does not retain `licenseNumber`, `licenseExpiryDate`, `sector`, the questionnaire answers, or the license file reference — those live only on the (terminal, no-longer-editable) application row. If the new platform needs this data queryable against the live association, this is a gap to design around, not just port.
2. **Temporary passwords are never persisted anywhere except the single RPC response** (both on application-approval and on password-reset) — by design, for security. This is a hard constraint to preserve in the NestJS migration: no logging, no DB column, no email-in-plaintext-stored-in-a-queue-table, etc. (the current system doesn't even say how the password reaches the association — presumably read aloud/copy-pasted by the admin reviewer, out of band).
3. **Extremely heavy defensive engineering around device/need transactions** (`commitDeviceWithNeed_`, `saveDeviceDescriptiveOnly_`) — manual snapshot/rollback simulating a DB transaction, because Google Sheets has no real transactions. In a real RDBMS-backed NestJS service this entire rollback-simulation layer (arguably ~150 lines of the 639) becomes unnecessary if wrapped in an actual DB transaction — worth flagging as intentional simplification opportunity rather than a feature to port literally, though the *business rules* it enforces (no orphan device states, no ghost devices, atomic device+need updates) absolutely must be preserved.
4. **Legacy back-compat function** `listAssociationApplications` (Applications.gs:347-350) is explicitly marked in a comment as being kept only for old callers and may be dead code — worth checking if any current UI still calls it before deciding whether to port it.
5. **Two different "already exists" duplicate checks** for applications: one blocks only against *pending* applications (email/phone/license), the other blocks against *any* existing user account by email. This means someone whose application was previously rejected CAN resubmit with the same email/phone/license (as long as no account exists and no other pending application conflicts) — this looks intentional (rejected applicants should be able to retry) but is easy to get wrong in a re-implementation if not read carefully.
6. **Update path of `saveAssociation` has no idempotency/lock protection**, only the create path does — this is a deliberate, explained asymmetry (update has no side-effect-creating risk like duplicate-account-creation), not an oversight, but worth confirming the same reasoning applies (or doesn't) in the new architecture.
7. **`generateTempPassword_`** (application-approval, format `Zad-xxxxxxxx-nnnn`) and **`generateStrongTempPassword_`** (password-reset path, format via `createAccessCode_`) are two separate, differently-formatted password generators for what is conceptually the same need (a temp password guaranteed to pass `assertStrongPassword_`). Minor duplication worth consolidating in the rewrite.
8. **Device detail's `assignedAt`/`dispatchedAt` are derived by regex-matching audit log note text**, not stored as columns. This is fragile (depends on exact Arabic phrasing used in audit notes elsewhere, e.g. `'← مخصص'`) and should become real timestamp columns in the new schema rather than being ported as-is.
9. Both files rely heavily on external functions not part of this audit's scope but essential to full behavior: `validateDeviceType_`, `validateRegionCity_`, `validateAssociationCategory_`, `validateAssociationSector_`, `planNeedTransitionsForDeviceChange_`, `assertDeviceTransition_`, `requireSession_`, `throttle_`, `withIdempotency_`/`runLockedIdempotent_`, `audit_`. These live in other .gs files (`ReferenceData.gs`, `StateRules.gs`, `DataUtils.gs`, etc.) and would need their own audit passes for full parity coverage — this document only covers what's directly visible in `Applications.gs` and `DevicesAssociations.gs`.
