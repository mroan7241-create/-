## Prose detail on complex/cross-cutting items

### Session lifecycle (full picture)
- **Creation**: `createSession_` (AUTH-008) on successful login only — no session created for a must-change-password rejection at `loginUser_`'s early-return point... actually it *is* created (token returned) but the account is functionally locked to only `changePassword`/`logout` by AUTH-009's role==='ASSOCIATION' check (see finding below).
- **Storage**: `CacheService.getScriptCache()` only — no persistent session table/sheet. This means restarting/redeploying the Apps Script project, or the cache simply evicting early (Google gives no hard guarantee), silently logs everyone out.
- **Idle timeout**: 6 hours, refreshed (slid forward) on every `requireSession_` call.
- **Absolute cap**: 12 hours from `issuedAt`, enforced by comparing wall-clock timestamps stored inside the session JSON — independent of the sliding cache TTL.
- **Server-side kill switch**: per-actor "epoch" counter (AUTH-006) — bumped on password change (self-service and reset-by-email), delegate code regeneration, and delegate deactivation. Any session issued before the bump is instantly invalid on its next `requireSession_` call, regardless of its remaining idle/absolute time.
- **Logout**: explicit deletion of the one session's cache key only (does not bump the epoch, so doesn't affect other devices' sessions).

### Password policy (AUTH-013)
- Minimum 10 characters.
- Must contain ≥1 letter and ≥1 digit (regex-checked; no uppercase/lowercase/symbol requirement beyond that).
- Cannot equal the current password.
- Cannot equal the immediately-previous password (one generation of reuse memory only — a password from two changes ago is not blocked).
- Same policy function shared by self-service change (AUTH-012) and email-code reset (AUTH-011), by design, to avoid drift.

### Delegate access codes
- Format: `MND-` + 6 alphanumeric characters drawn from an ambiguity-reduced alphabet (no `I/O/0/1`).
- Generated only by ADMIN/ASSOCIATION on delegate creation (DEL-002) or explicit regeneration (DEL-003) — never self-service, never re-displayable after creation (only the hash persists).
- Regeneration immediately invalidates the old code (full hash+salt replacement, not a soft flag) and force-logs-out any active delegate session via the epoch mechanism.
- Delegate deactivation (DEL-004, status → 'غير نشط') also force-revokes sessions immediately, independent of code regeneration.
- Login validation regex for codes is stricter than generation (`{6,12}` length window) — presumably to tolerate manually-typed/legacy codes of varying length even though current generation always produces exactly 6 characters after the prefix.

### Rate limiting / throttle inventory
| Action | Bucket key | Limit | Window |
|---|---|---|---|
| User login | `login:` + hash(email) | 8 | 900s (15 min) |
| Delegate login | `login:` + hash(code) | 8 | 900s |
| Password reset request | `pwreset-req:` + hash(email) | 5 | 900s |
| Password reset code verification | `pwreset-verify:` + hash(email) | 10 | 900s |
| Password reset code — separate per-payload attempt counter | stored inside the cached reset payload itself, not the generic throttle_ bucket | 6 | tied to the 15-min reset-code TTL |
| Delegate code regeneration | `regen-delegate-code:` + delegateId | 8 | 900s |

All buckets share the same `throttle_` primitive (AUTH-001); none are IP-based (Apps Script exposes no client IP), all key off the submitted identifier itself, hashed before being used as a cache key.

### Role isolation enforcement points
- **Association ↔ association isolation**: enforced independently in at least three places — `listDelegates_` (DEL-001), `buildAssociationPortal_` (BOOT-004), and every delegate-mutating function's explicit `String(existing['رقم الجمعية']) !== user.associationId` check (DEL-002, DEL-003, DEL-004). There is no single shared "scope query to my association" helper for delegates — each function re-implements the same ownership check inline.
- **Delegate ↔ own-beneficiaries isolation**: enforced per-function (DEL-006 through DEL-011), each independently comparing `رقم المندوب` to `user.id`.
- **Suspended-association lockout**: enforced at login (AUTH-007 called from AUTH-003/004) and again on every bootstrap fetch (BOOT-002 → `assertActorEnabled_`) — meaning a suspension applied mid-session takes effect within `APP.cacheSeconds` (60s) of the next dashboard refresh, not just at next login.

## Summary

Distinct callable features/business rules extracted: **33** (14 in AUTH-, 11 in DEL-, 5 in BOOT-, 3 in CFG-, 7 in UTIL- — note UTIL section includes generic-but-auth-gating utilities per the task's DataUtils.gs instruction). Several of these (AUTH-012 `changePassword`, UTIL-007 `requireMaintenanceAccess_`, BOOT-005 `clearDashboardCache`) live outside the five target files but were pulled in because Auth.gs/Bootstrap.gs/DataUtils.gs call them directly and they're inseparable from understanding the auth/session/bootstrap picture.

### Flags — unusual, contradictory, or under-documented

1. **`Bootstrap.gs` is not a first-run/setup file.** Despite its name and the task's framing ("bootstrap-time checks... first-run setup, admin seeding"), this file is entirely about building the initial *dashboard data payload* served to an already-authenticated user (role-scoped portal builders + caching), not application/schema initialization. The actual first-run schema-setup function is `setupSheets_` in `ReferenceData.gs` (not part of this file set), and admin seeding wasn't found in any of the five audited files — likely a manual/editor-run step outside the web app's callable surface, or elsewhere in the codebase not covered by this task. Worth flagging to whoever scoped the file list: `ReferenceData.gs` and possibly a dedicated setup/seed file may need a follow-up pass for true bootstrap-time gating logic.

2. **Must-change-password lock only checks `role === 'ASSOCIATION'`.** In `requireSession_` (AUTH-009), the forced-password-change lock is gated as `user.mustChangePassword && user.role === 'ASSOCIATION'`. But `loginUser_` (AUTH-003) sets/returns `mustChangePassword` generically for *any* user row with that sheet flag set, regardless of role — including, in principle, an ADMIN row. If an ADMIN account ever had `يجب تغيير كلمة المرور` = 'نعم', `loginUser_` would correctly withhold bootstrap data at login (its own `if (mustChangePassword) return {...}` check has no role condition), but that same admin's session, once created, would **not** be locked out of any other endpoint by `requireSession_` on subsequent calls, since the gate only fires for role ASSOCIATION. This looks like an asymmetry/latent gap rather than an intentional design (there's no comment explaining why ADMIN is excluded from the enforcement, only why must-change-password exists at all). Low real-world risk if admin accounts are never provisioned with that flag set, but worth verifying intent before porting the rule.

3. **Two independent idempotency mechanisms with materially different guarantees coexist** (`withIdempotency_` vs `runLockedIdempotent_`, UTIL-004) with the weaker, race-prone one (`withIdempotency_`) still used in delegate/delivery flows (`saveDelegate` create, `updateDeliveryStatus`, `retryDelivery`, `confirmDelivery`) while the codebase's own comments say the *stronger* locked version exists specifically because the weak one has a proven race window. It's not clear from these five files alone why the delivery/delegate flows weren't migrated to the stronger primitive too (the strong one seems to have been introduced later, for a different feature — beneficiary-needs review — per its comment) — possibly just not backported yet. Worth a deliberate decision when porting: the Node/NestJS equivalent should probably standardize on one mechanism (e.g., a real idempotency-key table with a unique constraint) rather than porting both.

4. **No durable session store; no durable idempotency ledger.** Both are explicitly self-documented in the source as deferred/backlog items (the idempotency ledger is explicitly called a "P1... before actual production launch" gap in a comment referencing `HANDOFF.md`). Session state living only in `CacheService` means a cache eviction/redeploy invisibly logs out every user with no warning — something to explicitly design around (not just replicate) in the Node platform, which will presumably back sessions with a real store (Redis/DB) instead.

5. **Password complexity is comparatively weak by modern standards** (10 chars + 1 letter + 1 digit, no symbol/case requirement) and password-reuse memory is only 1 generation deep. This is a policy decision worth explicitly confirming with stakeholders during migration rather than silently carrying it forward or silently tightening it.

6. **Delegates have literally no email/self-identifying credential recovery path** — losing a code requires an association staffer to intervene (DEL-003). This is a deliberate design (documented in comments) but is a UX/support-load consideration for the new platform.

7. **Duplicate-ID handling is a hard stop, not a self-heal.** `findById_`/`updateById_` throw rather than disambiguate when a sheet has two rows sharing an id (a scenario the comments say has happened in production, from copying the spreadsheet and Script Properties counters resetting). This is a strong signal the Node/SQL platform's migration must guarantee real uniqueness constraints (which the legacy Sheets backend structurally cannot enforce), and that any one-time data migration script should proactively dedupe/validate ids before import.
